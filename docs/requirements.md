# Mini React 요구사항

기준은 대화에서 제공된 JUNGLE 과제 원문 「미니 리액트 구현 / 요구사항」이다. 아래 ID는 저장소에서 작업과 검증을 연결하기 위해 붙였다.

| ID | 필수 동작 | 합격 기준과 확인 방법 |
| --- | --- | --- |
| P1-00 | 검증 화면 초기화 | 실제 영역의 샘플 DOM을 VNode로 읽어 수정 가능한 테스트 영역을 렌더링한다. 두 영역과 Patch·뒤로가기·앞으로가기 버튼을 브라우저에서 확인한다. |
| P1-01 | DOM → VNode 변환 | 합의한 지원 범위의 태그·속성·텍스트·자식 순서가 보존된다. 실제 DOM을 입력으로 주어 결과와 원본을 확인한다. |
| P1-02 | Diff와 Patch | 추가·삭제·교체·텍스트·속성 변경과 동일 트리를 검증하고 편집 후 Patch로 필요한 부분만 반영한다. 같은 위치의 미변경 노드 참조와 실패 시 상태 일관성을 확인한다. |
| P1-03 | 복합 변경과 회귀 검증 | P1-02의 기본 검증에 더해 중첩 추가·삭제, 위치 밀림, 빈 화면·여러 최상위 노드, 연속 편집을 검증한다. |
| P1-04 | 상태 이력과 Phase 1 통합 | 성공한 Patch의 새 VNode를 이력에 저장한다. 앞뒤 이동으로 두 영역을 복원하고 이력 경계·분기·무변경·실패 시 이력 보존을 검증한다. |
| P2-01 | 루트 컴포넌트 | `FunctionComponent`가 `hooks`, `mount()`, `update()`를 제공한다. 최초 렌더링과 상태 변경 후 재렌더링을 확인한다. |
| P2-02 | 부분 갱신 | 사용자 입력과 클릭이 상태를 바꾸고, Phase 1의 VNode·Diff·Patch를 재사용해 필요한 DOM 부분을 갱신한다. |
| P2-03 | `useState` | 다시 렌더링해도 상태를 보존하고 setter 호출 시 화면을 갱신한다. |
| P2-04 | `useEffect` | 확정한 실행 시점·의존성·정리 계약에 맞게 동작하는지 확인한다. |
| P2-05 | `useMemo` | 확정한 의존성 계약에 맞춰 값을 재사용하거나 다시 계산하는지 확인한다. |
| P2-06 | 루트 상태와 자식 props | 상태와 Hooks는 루트에서만 사용한다. 자식은 props만 사용하는 순수 함수다. |
| ENV-01 | 기술 제한 | 제품은 HTML·CSS·Vanilla JavaScript 또는 TypeScript로 구현한다. 제품 의존성에 외부 UI 프레임워크가 없는지 확인한다. |
| Q-01 | 모듈 검증 | 주요 모듈의 단위 테스트를 실행한다. |
| Q-02 | 기능 검증 | 실제 브라우저에서 두 Phase의 사용자 흐름과 경계 조건을 검증한다. |

Batching은 선택 과제다. Diff의 5가지 케이스에 대한 별도 공식 분류가 있는지는 확인이 필요하다. 지원 노드 범위, 이력 분기, Hook 의존성 등 구체적인 동작 계약은 [아키텍처](architecture.md)에서 결정 상태를 관리한다.

## 작은 작업의 순서

ID는 진행 상태가 아니다. 기존 구현의 유지·교체는 아래 예시를 함께 확인한 뒤 해당 동작의 범위에서 결정한다. 먼저 하나의 독립적인 동작을 구현·검증하고 사용자가 수용한 뒤 다음 동작으로 이동한다. 아래 순서는 자동 착수 허가나 새 설계의 승인을 뜻하지 않는다.

| 작업 | 선행 조건 | 먼저 볼 예시와 검증 |
| --- | --- | --- |
| P1-00 초기화 | 결정 0001 | 원본 샘플을 읽어 별도 편집 영역에 표시. 기존 DOM 검사와 브라우저 입력·원본 보존 검사를 재사용. P1-01 전체 수용과 구분 |
| P1-01 변환·렌더 | 결정 0001, 기존 초기화 코드 | `<p class="note">안녕</p>` → 요소·텍스트 VNode → 같은 구조의 새 DOM. 기존 변환을 재사용해 지원 범위·원본 보존 검사를 보완 |
| P1-02 Diff·Patch | P1-01, 결정 0003의 Diff·Patch 관련 계약 확정 | `안녕` → `반가워`의 텍스트 변경부터 확인. 이후 속성·추가·삭제·교체·동일 트리를 각각 검증하고 버튼·고정 데이터 루트·합의한 오류 처리를 연결. 이력 계약 확정·구현은 P1-04에서 진행 |
| P1-03 복합 변경 | P1-02, 복합 변경 사례와 기대 결과 확정 | 중첩·여러 형제의 위치 밀림·빈 화면·여러 최상위 노드·연속 편집 회귀 검사. 기본 변경 검증을 이 단계까지 미루지 않음 |
| P1-04 이력 | P1-02·P1-03, 결정 0003의 이력 계약 확정 | `A → B → 뒤로 A → 앞으로 B`. 경계·분기·무변경·실패 시 이력 보존을 검사하고 Phase 1 흐름 통합 |
| P2-01 루트 | Phase 1, VNode·이벤트·Hook 위치 계약 | `mount()`로 표시하고 명시적 `update()`로 변경. 최초 렌더와 공통 엔진 연결 검사. useState 선구현은 불필요 |
| P2-03·P2-06 상태·자식 | P2-01 | 버튼으로 `0 → 1`, 다시 렌더해도 상태 보존. 루트 Hooks·자식 props·자식 Hook 제한 검사 |
| P2-04 Effect | P2-01, 실행·의존성·정리 계약. 상태 변경에는 P2-03 활용 | 합의한 의존성 변경 전후의 실행·정리 순서를 기록해 검사 |
| P2-05 Memo | P2-01, 의존성 계약. 상태 변경에는 P2-03 활용 | 같은 의존성은 재사용하고 변경 시 재계산하는지 계산 횟수로 검사 |
| P2-02 통합 | P2-03·P2-04·P2-05·P2-06 | 입력·클릭·Effect·Memo 데모와 미변경 노드 참조로 Phase 1 엔진 재사용 확인 |

## Phase 1 완료 기준과 검증 연결

아래는 구현 작업의 완료 판단에 사용할 검사 계획이다. 현재 P1-00·P1-01 검사가 자동 실행에 연결되어 있다. 검사 등록은 통과·사용자 수용을 뜻하지 않으며 실제 결과는 해당 작업 보고에서 구분한다. P1-02 이후의 후속 검사와 수동 절차는 해당 기능을 구현한 뒤 실행하며, 아직 없는 검사는 미실행으로 남긴다.

| ID | 관찰할 합격 기준 | 검사 연결과 현재 범위 |
| --- | --- | --- |
| P1-00 | 실제 샘플을 별도 편집 DOM으로 초기화하고 편집해도 원본과 원본 노드 참조는 유지. 버튼의 표시·비활성화와 초기화 실패 구분 | `tests/browser/p1-00.html`의 초기화 기능 5개와 `p1-00.spec.js`의 입력·삭제·원본 보존 검사를 실행. 공통 변환·렌더 검사와 함께 Playwright 4개로 실행하며 검사 자체의 실패 감지도 포함 |
| P1-01 | 합의한 태그·문자열 속성·텍스트·공백·자식 순서·template 보존, 주석 제외·지원 밖 입력 거부, 입력 DOM 무변경과 별도 DOM 생성 | `tests/unit/vdom.test.js`의 변환·렌더 27개를 `tests/browser/p1-00.html`에서 실행하고 `p1-00.spec.js`가 초기화 5개를 포함한 전체 32개의 결과를 확인. 중첩·빈 template, 빈·연속 텍스트, 실제 문자, 폼 속성 범위, VNode·DOM 독립성과 오류 시 원본 보존을 포함. 사용자 수용은 별도 확인 |
| P1-02 | 추가·삭제·교체·텍스트·속성·동일 트리에서 예상 변경과 반영 결과 일치. Diff 입력 무변경, 같은 위치의 미변경 노드 참조 유지, 합의한 실패 시 상태 일관성 | 순수 Diff 검사와 실제 DOM Patch·버튼 연결 검사 추가 예정. 주석·공백·template 경로, 잘못된 경로, 합의한 오류 처리 사례도 포함 |
| P1-03 | 중첩·여러 형제 추가/삭제·위치 밀림·빈 화면·여러 최상위 노드·연속 Patch가 합의한 비교 범위에서 일치 | 복합 변경 회귀 검사 추가 예정. 단일 성공뿐 아니라 이전 경로 재사용 오류와 반복 실행 후 상태를 확인 |
| P1-04 | 초기 이력·양 끝 버튼·앞뒤 복원·분기·무변경·실패 시 이력 보존이 확정한 계약과 일치하고 두 영역의 표시 상태도 일치 | 순수 이력 검사와 전체 브라우저 흐름 검사 추가 예정. 미확정 편집 처리도 확정한 기대 결과로 검사 |

추가한 모듈 검사는 브라우저 실행 페이지나 Playwright 검사에서 실제 호출되도록 연결하고, `npm test`의 결과에 포함되는지 확인한다. 최종 실행은 `npm run verify`를 사용하며 명령의 현재 범위는 [README](../README.md#실행과-검증)가 원본이다. 실행되지 않은 검사 파일이나 구문 검사 통과를 제품 기능의 통과로 기록하지 않는다.

Phase 1 통합 수동 절차는 **기준 A → 편집 B → Patch → 편집 C → Patch → 뒤로 B → 뒤로 A → 앞으로 B → 새 편집 D → Patch**다. 각 단계에서 두 영역·버튼·이력 위치가 확정한 계약과 맞는지 확인한다. 무변경 Patch와 오류 주입 검사는 이력 추가·위치·화면에 미치는 영향을 별도로 확인한다. 한글 조합 입력·포커스 이동·시각적 사용성도 수동 확인하며 자동 검사 결과와 구분한다. 이 절차는 후속 기능 구현 후 실행할 계획이다.

과제 원문의 Diff 5가지 케이스 분류는 아직 대조가 필요하다. 현재 프로젝트의 추가·삭제·교체·텍스트·속성 분류를 공식 분류 확인 결과로 쓰지 않는다. 필수 사례의 누락·실패·미실행과 사용자 수용 여부를 구분해 보고하며 요구사항·예시·테스트 기대값이 다르면 계약부터 확인한다.

담당·진행 상태는 실제 Jira 이슈로 확인하고 수용·Git 실행·결과 기록은 [개인 작업 정책](../TEAM_DEVELOPMENT_RULES.md)을 따른다. 구현 완료·테스트 통과·사용자의 이해·사용자 수용은 각각 구분한다.
