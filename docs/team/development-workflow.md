# 개발 흐름과 Git·PR 규칙

> **팀 검토 전 초안.** [팀 개발 규칙 목차](../../TEAM_DEVELOPMENT_RULES.md)

## 작업 시작과 분담

1. JUNGLE Compass에서 해당 Phase의 요구사항, 기술 제한, 제출 및 완료 기준을 확인한다.
2. 담당 Jira 이슈를 만들거나 기존 이슈를 확인한다. 담당자, 일정, 구현 범위, 완료 기준, 관련 작업과의 의존 관계를 기록한다.
3. 저장소의 `AGENTS.md`, 관련 코드, 합의한 설계와 공통 실행·테스트 방법을 읽는다. 구현 전에 모듈 간 입력·출력과 연결 지점을 팀과 맞춘다.
4. 현재 브랜치와 미커밋 변경을 확인하고, 원격 기본 브랜치의 최신 코드를 기준으로 개인 작업 브랜치를 만든다. 기존 작업을 이어갈 때는 해당 작업 브랜치와 Jira 이슈가 일치하는지 확인한다.
5. 같은 파일을 동시에 수정할 때는 변경 범위를 공유한다. 분담이나 일정이 바뀌면 팀과 논의하고 Jira를 갱신한다. 공통 변경은 수정한 위치와 영향을 기록한다.

### 팀 검토 필요 · `main` / `master`

기존 규칙의 작업 시작과 통합 절차에는 `main`, 리뷰·병합 절차에는 `master`가 쓰였다. 이 문서에서는 **기본 브랜치**로 표기한다. 팀은 GitHub에서 실제 기본 브랜치와 브랜치 보호 설정을 확인한 뒤 문서, PR 대상 브랜치, CI와 Jira 자동화 조건에 같은 이름을 적용한다.

## 브랜치와 커밋

- 공동 저장소에서 팀원별 독립 브랜치를 유지한다. 각자 AI 에이전트를 활용해 구현·테스트하고, 구현 비교가 끝날 때까지 브랜치를 보존한다.
- 개발 중에는 기본 브랜치에 직접 커밋하거나 Push하지 않는다. 팀원은 본인 브랜치에 Push하며, 다른 팀원의 구현에 변경이 필요하면 해당 팀원과 먼저 협의한다.
- 팀은 개인 구현의 요구사항 충족도, 검증 결과, 코드 구조를 비교해 최종 통합 대상을 결정한다. 선정한 변경을 통합 PR에 담고, 병합한 기본 브랜치에서 최종 실행·검증을 한다. 추가 정리가 필요하면 후속 PR로 반영한다.

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 팀원별 독립 브랜치 | `<유형>/<Jira 이슈키>-<소문자 이니셜>-<기능 설명>` | `feat/KJF-1-ym-mini-react`, `feat/KJF-2-yj-mini-react` |
| 기능 브랜치 | `<유형>/<Jira 이슈키>-<기능 설명>` | `feat/KAN-7-alarm-clock`, `fix/KAN-6-priority-donation`, `docs/KAN-5-build-guide` |
| 커밋 메시지 | `<유형>: <설명>` | `feat: Virtual DOM 변환 구현`, `refactor: Patch 로직 함수 분리`, `test: useMemo 의존성 비교 테스트 추가` |

브랜치의 기능 설명은 짧은 영문 소문자와 하이픈으로 작성한다. 커밋 하나에는 한 가지 목적을 담는다.

터미널에서 브랜치를 만들 때는 `git status --short`로 작업 상태를 확인하고 `git fetch origin`을 실행한다. 확인된 기본 브랜치를 `DEFAULT_BRANCH` 자리에 넣어 `git switch -c feat/KJF-1-ym-mini-react origin/DEFAULT_BRANCH`로 생성한다.

| 유형 | 용도 |
| --- | --- |
| `feat` | 기능 구현 |
| `fix` | 오류 수정 |
| `refactor` | 외부 동작을 유지하는 코드 개선 |
| `test` | 테스트 추가 및 수정 |
| `docs` | 문서 작성 및 수정 |

## 코딩 컨벤션

- 팀이 합의한 JavaScript 또는 TypeScript 스타일을 따르고 들여쓰기, 세미콜론, 따옴표, 파일명과 폴더 구조를 일관되게 유지한다.
- 함수와 변수의 이름에 역할을 드러낸다. 복잡한 함수는 책임에 따라 나누고, 불필요한 중복을 줄인다. 주석에는 코드만으로 드러나기 어려운 설계 이유와 제약을 적는다.

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 변수 | `camelCase` | `previousVNode` |
| 함수 | `camelCase` | `createVirtualDOM` |
| 클래스 | `PascalCase` | `FunctionComponent` |
| 상수 | `UPPER_SNAKE_CASE` | `MAX_HISTORY_SIZE` |
| 일반 JS·TS 파일 | `camelCase` | `diffAlgorithm.js` |

### 주석 작성 규칙

아래 주석 규칙은 사용자가 요청한 현재 개인 구현 작업에 적용한다. 팀 전체의 나머지 협업 규칙은 검토 전 초안 상태를 유지한다.

- **언어:** 설명 주석은 한글로 작성한다. 함수·변수·DOM API 이름과 `VNode`, `props` 등 식별자는 원래 표기를 유지한다.
- **함수 계약:** 공개 함수와 핵심 로직의 시작에 JSDoc으로 역할·입력·반환값·부작용·예외·지원 범위를 적는다. 변환 함수는 변환 전후 형태의 짧은 예시를 필요한 경우 포함한다.
- **실행 흐름:** 재귀 호출, 노드 유형 분기, 데이터 변환, DOM 반영, 비동기 순서처럼 이해가 필요한 처리 단계에 주석을 둔다. 현재 값이 어디서 오고 다음 단계에 무엇을 넘기는지 설명한다.
- **설계 이유:** 왜 이 API나 자료구조를 사용하는지, 어떤 조건을 보존하는지 적는다. 예를 들어 `createTextNode`의 텍스트 처리, 공백 보존, template의 `content`, 패널과 샘플 루트의 구분을 설명한다.
- **검증 코드:** 테스트가 확인하는 조건과 실패가 의미하는 바를 설명한다. 자동 검사가 다루지 못하는 실제 키보드 입력·브라우저 차이 등은 한계로 명시한다. 주석이나 테스트 작성 사실을 실행·통과 증거로 쓰지 않는다.
- **상세함의 기준:** 학습자가 핵심 흐름을 코드와 연결해 설명할 수 있는 수준으로 작성한다. 단순 대입·반복문의 문법을 매 줄 되풀이하기보다 의미 있는 처리 묶음을 설명한다.
- **정확성·갱신:** 실제 코드와 확정 계약에 근거한다. 미구현 동작을 구현된 것처럼 설명하지 않고 `TODO`에는 남은 일과 관련 요구사항을 적는다. 코드와 동작 계약을 바꾸면 관련 주석도 갱신한다. 설계 결정의 상세 근거는 `docs/decisions/`를 참조한다.

## PR, 리뷰와 병합

- 제목은 `[Jira 이슈키]: <유형> - <설명>` 형식으로 작성한다. 예시는 `[KJF-1]: feat - Virtual DOM 변환 구현`이다. 소문자 유형을 사용하고, 제목의 키를 작업 브랜치의 Jira 이슈키와 일치시킨다. PR 하나는 원칙적으로 Jira 이슈 하나를 다룬다.
- 개인 구현을 비교하는 PR과 기본 브랜치에 반영하는 최종 통합 PR은 목적과 대상을 구분해 표시한다.

| PR 본문 항목 | 기록할 내용 |
| --- | --- |
| **Summary** | 해결하는 문제와 구현 목적 |
| **Changes** | 주요 변경, 관련 모듈과 설계 변경 이유 |
| **Test Results** | 실행 명령, 단위·기능·회귀·경계 조건 검증 결과, 미실행 항목과 사유 |
| **Review Points** | 리뷰어가 확인할 핵심 로직, 논의할 설계와 남은 제약 |

1. 작성자는 관련 담당자나 다른 팀원에게 리뷰를 요청한다. AI 리뷰 결과는 팀원이 참고한다.
2. 최소 1명의 팀원 승인, 필수 리뷰 지적 사항 해결, 관련 테스트 통과를 확인한다. 기존 기본 코드에서도 재현되는 실패와 이번 변경으로 생긴 실패는 구분해 기록한다.
3. 최종 통합 대상은 팀이 선정한다. 작성자는 승인 조건을 확인하고 PR을 통해 병합한다. 기존 초안의 병합 방식은 `Merge`이며, 실제 저장소에서 사용할 방식은 팀 검토 시 확인한다.
4. 구현 이슈의 `완료` 전환은 최종 통합 PR이 기본 브랜치에 병합되고 Jira 완료 기준을 충족했을 때만 진행한다.
