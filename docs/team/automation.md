# Git·Jira 자동화와 승인

> **팀 검토 전 초안.** [팀 개발 규칙 목차](../../TEAM_DEVELOPMENT_RULES.md)

자동 실행 전에는 [검증 게이트](verification.md)와 [브랜치·PR 규칙](development-workflow.md)을 확인한다. Jira 상태를 다룰 때는 [이슈 관리 기준](jira-issues.md)도 확인한다.

## Git·Jira 자동화와 사람의 승인

| 작업 | 실행 기준 |
| --- | --- |
| Git 상태·Diff·브랜치 확인, 테스트, 형식·범위 검사 | 자동 실행 가능 |
| 요구사항 구현 요청에 따른 Jira Task 생성 | 현재 개인 작업은 [자동 이슈 연결 절차](jira-issues.md)의 승인 범위에 따라 중복 확인 후 KJF-2 아래에 생성·재조회한다. 계획·설계 검토 요청은 제외하며, Jira 상태 변경이나 Git 쓰기 권한으로 확대하지 않는다. |
| 본인 작업 브랜치 생성 | 작업 계약을 승인받고 이슈키·브랜치 이름·기준 브랜치를 확인한 뒤 조건부 실행 |
| Staging·Commit | 승인된 자동화 범위에서 필수 검증을 통과한 작업 파일만 스테이징하고 커밋 규칙을 적용 |
| Push | 사용자 승인 또는 사전에 승인된 정책의 범위에서 본인 브랜치에 실행 |
| PR 생성 | Push가 완료되고 검증, 대상 브랜치, Jira 키, 본문 기준을 충족한 경우 승인된 정책에 따라 실행 |
| Jira와 GitHub 연결·상태 갱신 | 실제 동작이 확인된 기존 연동을 우선 재사용한다. 브랜치·PR의 이슈키 연결을 확인하고, 상태 전환은 합의된 조건에 따라 실행한다. 연동이 없거나 확인할 수 없으면 Jira에 직접 링크와 상태를 기록한다. |
| Jira `완료` 전환 | 최종 통합 PR의 기본 브랜치 병합과 이슈 완료 기준 충족이 모두 확인돼야 한다. 기존 규칙이 모든 PR 병합에 반응한다면 비교용 PR을 제외하도록 조건을 검토한다. 완료 기준 충족 여부를 자동으로 판단할 근거가 없으면 담당자가 확인해 전환한다. |
| 주요 아키텍처 변경, 최종 통합 대상 선정, 다른 팀원 브랜치 변경, PR 병합 | 팀 또는 해당 권한을 가진 사람이 명시적으로 승인한다. 팀원 리뷰 승인과 CI 통과를 확인한 뒤 사람이 병합한다. |
| Force Push, Hard Reset 등 파괴적인 Git 작업 | 기본 금지. 예외는 영향 범위를 확인한 뒤 명시적으로 승인받는다. |

승인된 쓰기 작업을 실행했으면 브랜치, 커밋, Push·PR 결과와 Jira 변경을 작업 기록에 남긴다. 사용자나 팀원의 기존 변경을 보존하고 작업에 포함되는 파일을 선별한다.
