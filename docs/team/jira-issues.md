## 개인 구현 작업의 자동 이슈 연결

이 절차는 사용자가 승인한 현재 개인 구현 작업에 적용한다. 나머지 팀 운영·Epic 계층 규칙은 팀 검토 전 초안이다. 단순 구현 요청에도 작업 계약과 Jira 이슈를 연결하며, 별도 자동화 서버나 라이프사이클 훅 없이 Codex가 작업 절차로 실행한다.

### 적용 범위와 기본 대상

- 트리거: `P1-00 구현해줘`처럼 저장소 요구사항의 구현을 요청한 경우. 계획·설계 리뷰·설명만 요청하면 이슈를 생성하지 않는다.
- 기본 대상: `https://kylekim0868.atlassian.net`의 프로젝트 `KJF`, 상위 Epic `KJF-2 / YM-mini-react`, 이슈 유형 `Task`(현재 Jira 표시명 `작업`). 사용자가 다른 대상을 지정하면 그 지시를 우선한다.
- 이 범위의 신규 Task 생성은 사용자 승인된 작업 절차다. 대상과 작업 계약이 명확하면 생성 직전에 같은 허락을 반복해서 요청하지 않는다. 대상이 불명확하거나 기존 이슈와 범위가 겹치면 먼저 확인한다.

### 실행 순서

1. 관련 요구사항과 아키텍처를 읽고 작업 범위·합격 기준·검증 계획을 정리한다. 구현에 필요한 미정 계약은 사용자와 확인한다. 이미 확정한 계약은 재사용한다.
2. 사용자가 이슈키를 제공했으면 해당 이슈의 실제 내용과 상위 Epic을 읽는다. 이슈키가 없으면 대상 Epic 아래에서 요구사항 ID·제목·본문을 검색해 같은 작업이 있는지 확인한다. 같은 작업이면 기존 이슈를 재사용한다. 후보가 여러 개거나 유사 이슈의 범위가 불명확하면 중복 생성 전에 확인한다.
3. 같은 작업이 없으면 아래 형식으로 제목·본문을 구성해 새 Task를 생성하고 상위 Epic을 연결한다. **이슈키는 Jira가 생성한 반환값을 사용하며 임의로 번호를 만들지 않는다.**
4. 생성 후 다시 조회해 제목·본문·이슈 유형과 상위 Epic을 확인한다. 반환이 불명확하거나 시간 초과가 발생하면 먼저 생성 여부를 검색하고 재시도하여 중복을 방지한다. 실패 시 준비한 제목·본문과 실패 사유를 보고하고, 이슈 연결을 해결한 뒤 구현을 진행한다.
5. 확인된 이슈키·URL을 사용자에게 알리고 작업 계약·설계 기록에 연결한 뒤 구현·검증을 진행한다. 종료 시 검증 결과와 미검증 범위를 해당 이슈 및 후속 PR에서 참조할 수 있게 보고한다.

### 생성할 내용

- 제목: `[Phase 1] P1-00 검증 화면 초기화 구현`처럼 Phase·요구사항 ID·작업명을 포함한다.
- 본문: **구현 요구사항 / 승인한 설계 계약 / 작업 범위 / 제외 범위 / 완료 기준 / 검증 계획 / 관련 작업과 기록**을 구분한다.
- 완료 기준은 관찰 가능한 체크리스트로 작성한다. 아직 실행하지 않은 테스트는 계획으로 표시하며 통과했다고 기록하지 않는다.
- 본문에 상위 Epic, 현재 작업 브랜치, 관련 문서·의존 작업을 연결한다. 담당자·개별 일정은 사용자 지정값을 사용하고 미지정 값을 임의로 확정하지 않는다.

자동 Task 생성은 기존 이슈의 제목·본문·상위 관계 수정, 상태 변경, Epic 생성, Git 브랜치 생성·전환, 커밋·Push·PR·병합의 포괄 승인이 아니다. 해당 작업은 기존 사용자 지시와 승인 범위를 따른다. 특히 개인 통합 브랜치를 새 Task 키에 맞춰 임의로 바꾸지 않는다.

현재 P1-00은 [KJF-14](https://kylekim0868.atlassian.net/browse/KJF-14)로 생성했고 상위 Epic이 KJF-2임을 재조회로 확인했다. 같은 P1-00 작업을 이어갈 때 이 이슈를 재사용한다.

## Jira 이슈

- 개발 작업은 Jira 이슈 단위로 관리한다. 작업 범위, 상태, 테스트 결과, 관련 브랜치·PR과 최종 통합 이력을 추적한다.
- 제목 형식은 `[Phase 또는 분류] 기능 또는 작업명`을 사용한다. 예시는 `[Phase 1] Diff 알고리즘 구현`, `[Phase 2] FunctionComponent 구현`, `[Integration] Phase 1 최종 코드 통합`, `[Test] 전체 기능 검증`이다.
- 본문에 **구현 요구사항**과 **완료 기준**을 분리해 적는다. 예를 들어 Diff 작업의 요구사항에는 노드 추가·삭제·교체, 텍스트·속성 변경, 중첩 노드 비교를 명시한다. 완료 기준에는 동일 트리의 변경 없음과 각 변경 유형의 테스트 통과를 적는다.

| 유형 | 용도 |
| --- | --- |
| Epic | 큰 개발 범위를 묶는다. 어떤 단위로 나눌지는 팀 검토 후 확정한다. |
| Task | 기능 구현과 일반 개발·통합·검증 작업 |
| Bug | 오류 수정 |
| Sub-task | 상위 이슈의 구현이나 검증을 더 세분화할 때 사용 |

### 팀 검토 필요 · Epic 계층

기존 규칙은 프로젝트 전체를 단일 Epic으로 관리한다고 설명하면서, 이슈 유형 표에서는 Phase별 범위를 Epic의 용도로 제시했다. 예시의 `YJ-mini-react`가 팀원별 독립 구현을 나타내는지도 확인이 필요하다. 팀은 **프로젝트 단일 Epic / 팀원별 Epic / Phase별 Epic** 중 운영 방식을 정하고, 기능 Task·통합 Task의 상위 이슈와 최종 완료 기준을 확정한다. 확정 전에는 자동으로 Epic을 생성하거나 기존 이슈의 상위 관계를 변경하지 않는다.

| 분류 | 기능 Task 후보 |
| --- | --- |
| Phase 1 | DOM → Virtual DOM 변환, Diff, Patch, State History, 테스트 페이지 |
| Phase 2 | `FunctionComponent`, `useState`, `useEffect`, `useMemo` |
| 통합·검증 | Phase 1 통합, Phase 2 통합, 전체 기능과 경계 조건 검증 |
