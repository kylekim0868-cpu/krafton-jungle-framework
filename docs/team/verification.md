# Codex 작업 계약과 검증

> **팀 검토 전 초안.** [팀 개발 규칙 목차](../../TEAM_DEVELOPMENT_RULES.md)

## Codex 작업 계약과 하네스

Codex는 요구사항 분석, 설계 제안, 구현, 테스트, 변경 기록을 맡을 수 있다. 설계 검토를 요청한 작업은 제안과 결정 사항 정리까지 진행한다. 구현 요청은 합의된 범위에서 동작하는 결과물과 검증까지 진행한다. 확정 아키텍처나 모듈 간 계약에 중요한 변경이 필요하면 영향과 대안을 제시하고 사람의 결정을 받는다.

작업 시작 전에 Jira 이슈 또는 연결된 문서에 다음을 정의한다.

- **입력** — 적용할 Phase 요구사항, 기존 구현과 설계 결정, 작업 대상과 의존 관계
- **범위** — 수정할 기능·파일, 유지할 인터페이스와 동작, 이번 작업에서 제외할 항목
- **합격 기준** — 사용자에게 보여야 할 동작, 정상·경계 사례와 회귀 조건, 검증 명령 또는 브라우저 재현 절차
- **증거** — 변경과 요구사항을 연결하는 PR, 실제 테스트 결과, 미검증 범위, 검토가 필요한 결정

| 검증 영역 | 확인할 기준 |
| --- | --- |
| Phase 1 | DOM 변환과 렌더링, Diff·Patch의 추가·삭제·교체·텍스트·속성 변경, 중첩 구조, Patch와 뒤로·앞으로 이동, 이력 경계와 과거 상태에서 새로 수정하는 경우 |
| Phase 2 | 루트 `FunctionComponent`의 `mount()`·`update()`와 Hook 상태 보존, props만 사용하는 자식, 상태 변경 후 Phase 1 Diff·Patch 재사용, Effect의 실행·정리, Memo 의존성 변경과 재계산 |
| 협업 절차 | 요구사항과 합격 기준의 연결, 실제 검증 실행 여부, 주요 설계 변경의 승인·기록, 다음 작업에서 재사용할 기록 |

필수 검증의 상태는 `통과`, `실패`, `미실행`으로 구분한다. 코드 구현 여부와 검증 여부를 따로 보고하며, 미실행에는 이유와 확인할 항목을 적는다. 테스트가 다루지 못한 동작은 브라우저 확인이나 사람의 리뷰로 보완한다. HTML·CSS·JavaScript 또는 TypeScript 범위에서 구현하고 외부 UI 프레임워크는 사용하지 않는다. Batching은 선택 과제로 관리한다.

## 개별 구현 작업의 검증과 수용

아래 네 규칙은 사용자와 합의한 현재 Codex 작업에 적용한다. 문서의 나머지 팀 운영 절차는 팀 검토 전 초안 상태를 유지한다.

1. **AI가 수정·재검증한다.** 합의한 범위의 구현 오류는 Codex가 원인을 분석하고 수정한 뒤 관련 검증을 다시 실행한다. 범위 안의 오류 수정마다 사용자 승인을 기다리지 않는다. 테스트의 기대값이 계약과 다르면 계약을 근거로 테스트를 바로잡으며, 통과를 위해 합격 기준을 임의로 낮추지 않는다. 해결하지 못한 실패는 원인·시도·남은 문제를 보고한다.
2. **계약이 모호하면 확인한다.** 기대 동작을 정할 수 없거나 확정 계약의 변경이 필요하면 미결정 사항·영향·대안을 제시하고 사용자에게 결정을 요청한다. 결정이 필요한 구현은 보류하되 독립 작업은 진행한다. 실행 환경 때문에 검사하지 못한 경우는 계약 모호성이나 제품 실패와 구분하여 미실행 사유를 보고한다.
3. **검증과 수용을 구분한다.** Codex는 합격 기준별 통과·실패·미실행, 실제 실행 명령 또는 재현 절차와 결과, 미검증 조건을 보고한다. 테스트 통과만으로 요구사항 전체 충족이나 사용자 수용을 선언하지 않는다. 사용자가 증거와 필요한 직접 확인 결과를 검토해 해당 작업의 최종 수용을 판단한다. 이 수용은 PR 병합 승인이나 Jira 완료 전환과 별개다.
4. **수용 후 다음 작업으로 이동한다.** 단계별로 진행하는 작업은 결과 보고 후 사용자의 수용 확인을 받고 다음 기능에 착수한다. 필수 검증의 실패·미실행이 남아 있으면 수용 대기로 넘기기 전에 보완하거나 제약을 명시한다. 다음 작업은 번호순으로 단정하지 않고 의존 관계와 재사용할 확정 계약을 근거로 제안한다. 여러 작업의 연속 수행을 사용자가 이미 명시적으로 승인했다면 그 승인 범위를 따른다.

## 라이프사이클 훅과 검증 게이트

저장소에서 사용하는 명령과 CI 실행 조건을 확인해 각 검증 항목에 연결한다. 예를 들어 `git status --short`, `git diff --check`, `git diff --cached`로 상태와 변경을 확인한다. 기능·회귀 테스트에는 프로젝트에 등록된 실제 명령을, 수동 검증에는 재현 절차를 기록한다.

| 실행 시점 | 자동 확인 또는 수동 실행 절차 | 통과 기준과 실패 시 처리 |
| --- | --- | --- |
| 작업 시작 | Jira 범위와 완료 기준, 설계, Git 상태, 원격 기본 브랜치와 본인 브랜치를 확인한다. | 대상·범위가 분명하고 기존 변경을 보존할 수 있어야 한다. 브랜치가 불명확하거나 기존 변경과 겹치면 Git 상태를 바꾸기 전에 확인한다. |
| 코드 변경 후 | 변경 파일·Diff·민감 정보 포함 여부를 검사하고, 관련 단위·기능·회귀 테스트와 필요한 브라우저 검증을 실행한다. | 범위 이탈과 실패를 확인하면 원인을 조사한다. 기존 실패 여부를 기록하고, 필수 검증이 실패했거나 미실행이면 자동 커밋·Push·PR 생성을 중단한다. |
| 작업 종료 | 변경과 검증 결과를 요약하고, 작업 파일만 스테이징한 뒤 스테이징된 Diff를 다시 확인한다. 허용된 경우 커밋·Push·PR 생성을 진행하고 이력을 기록한다. | 검증 통과, 작업 범위와 Jira 키 일치, 각 쓰기 작업의 권한을 확인한다. 실패 지점과 이미 실행한 작업을 기록하고 해당 단계에서 멈춘다. |
| PR 업데이트·병합 전 | PR의 현재 변경 기준으로 CI 결과와 리뷰 상태를 확인한다. | 필수 검사와 팀원 승인, 지적 사항 해결이 필요하다. 변경이나 검사 실패로 조건이 충족되지 않으면 검증을 다시 거친다. 병합 판단은 사람이 맡는다. |

- **Codex 실행 절차**는 작업 맥락을 읽고 구현 전후 검증과 결과 기록을 연결한다. 현재 환경에서 지원과 설정이 확인된 Codex 훅만 자동 실행에 사용한다. 나머지 절차는 명시적으로 실행하거나 체크리스트로 확인한다.
- **Git Hooks**는 로컬 커밋 전 검사처럼 Git 이벤트에서 실행하는 검증에 사용한다. **GitHub Actions**는 PR의 공통 테스트와 회귀 검증을 수행한다. 각 실행 위치와 검사 범위를 기록하고, 필수 검사 적용 여부는 저장소 설정에서 확인한다.
- 자동화 도입은 환경 확인, 실행 범위와 게이트 설계, 팀 승인, 최소 구성 적용 순서로 진행한다. 기존 훅과 CI부터 확인하고 미니 리액트 구현과 검증에 필요한 범위로 제한한다.
